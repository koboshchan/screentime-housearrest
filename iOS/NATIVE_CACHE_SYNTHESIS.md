# Emergency safety quarantine

Production helper Apply and cache planning are disabled unconditionally before any reads, backup, refresh, or write. This includes apparently populated Daily/Weekly caches: older builds may have synthesized them, and file presence cannot prove provenance or completeness. No UI or request flag bypass exists.

This is containment, not a validated reconstruction algorithm. Historical transformations remain exercised under HOST_STORAGE_TEST on disposable fixtures only. Missing weekly observations are not proven zero, hourly totals are not interchangeable with native Daily/Weekly, and category semantics remain unresolved. Cloud propagation of applied usage is user-reported; propagation of incomplete weekly caches is unverified.

Installing this fix does not undo prior Apply, reset future metadata, restore history, or modify existing usage. A separate read-only backup comparison is required.
Native cache synthesis uses this device's existing Local/Hourly schema and calendar settings. No VM identity, sample usage, or Python proof data is imported into the app.

The schema reference was inspected locally on the Mac in 24hplus/patched_DeviceActivity/Local. The proof's metadata processing changes only lastUpdatedDate; the remaining native metadata retains Hourly/Daily/Weekly segmentInterval values 0/1/2, a common UUID recordName prefix with the granularity suffix, and identical device/user objects. Native segment value keys match across the three granularities. The current XS Max Hourly value and metadata were independently checked read-only and match that structure. Raw reference/device contents remain private and untracked.

A missing Daily uses a stripped blank native segment plus the exact selected sessions' per-app durations. When a Weekly already exists, the old Daily baseline is taken from the existing Daily or the sum of observed selected-day Hourly app durations, and the Weekly delta preserves its other-day amounts. Negative/inconsistent deltas fail before backup.

A missing Weekly uses the device's LocalTimeZone and LocalFirstWeekday with Gregorian calendar arithmetic, including DST. It adds the edited day to all observed outside-day native Daily app totals, or Hourly app totals where a Daily is absent. The two representations are never double counted. Conflicting intervals, an outside-day Daily smaller than any observed hourly app total, unknown template fields, invalid metadata, or missing Hourly baseline fail closed. Missing historical observations are not invented usage; all observed outside-day app durations are retained. No existing containing Weekly is replaced by a newly inferred baseline.

New records omit recordSystemFields/recordName/recordID, firstPickup and longestActivity from cloned segment values. New metadata derives enum and recordName suffix from this device's validated Hourly metadata and omits its CloudKit system fields. Device/user objects come only from this device, not a reference fixture.

Planning does not create directories or mutate any usage or metadata. Existing native directories are required. The source inventory binds calendar files, explicit missing Daily/Weekly segment paths and missing metadata into the existing fingerprint and independently verified backup. O_EXCL/O_NOFOLLOW creates only the paths still absent after backup and revision checks. Existing files retain byte-concurrency checks. Synthetic regression tests verify absence receipts and restoration of the exact source revision after removal of all newly created fixture paths.

Live XS Max validation is read-only. It verifies overlapping 1h+1h yields 7200 seconds in both missing Daily and missing Weekly plans, native metadata enums 1/2, stripped system identity, and explicit absence inventory entries. It never calls Apply, backup, or any usage write. Settings rendering after an actual Apply remains a user-driven acceptance step.

After the both-missing read-only preflight, iOS naturally generated native Daily and Weekly on the XS Max, without an Apply from this work. A separate structural-only validator read those real records on-device and confirmed equal value-key schema across all three granularities. It also compared the synthesized metadata to the native Daily/Weekly metadata and verified exact device, user, recordName and segmentInterval equality. No raw cache contents or identities were exported. This validates the derivation against current native records on the actual target phone, not just the older local reference. The separate RootHide 03-clone VM was then reached using a pinned-key direct tunnel after its SSH relay stalled. Its real Hourly/Daily/Weekly schemas and exact derived metadata fields also passed the structural-only validator. The final RootHide package was installed and launched, and the app's newly generated authenticated helper status reported ok=true, code=ready. The previous Surface bundle was preserved, the older ScreenTimeEditor app's executable checksum remained unchanged, and no Apply was performed.
