# Native baselines and overlapping app sums

Apply requires matching native Daily and enclosing Weekly baselines. If Local is missing these for today's full native calendar day, it can promote validated same-device native Cloud baselines. It never reconstructs Daily or Weekly from sparse Hourly observations. Missing history is unknown, not zero. Weekly per-app values retain their native outside-selected-day contribution and only replace the selected-day contribution.

Category and segment duration totals are recomputed as app sums including overlap, without a per-hour or per-day cap. Web data and all unrelated category/app fields remain intact, but web durations do not add duplicate time. Newly introduced categories use their app sum instead of zero.

Future refresh metadata is the normal Gemini bypass, not proof of unsafe provenance. A verified Surface archive explicitly recording the baseline as absent, combined with exact reconstruction of the old identity-stripped synthesized output, rejects a known legacy synthetic baseline. Native regeneration is not blanket rejected just because an older absence archive exists. No device Apply or restore is part of release verification.

The production planner has no HOST_STORAGE_TEST safety bypass. The host fixture constructor only supplies disposable filesystem paths; it invokes the identical planner and guards. Tests exercise valid unequal native categories, exact summed category aggregates and byte-equal unrelated fields, weekly outside-day deltas, missing baselines before writes, longer future timestamps, and verified legacy-synthesis provenance.


The Cloud fallback is restricted to today. LocalDeviceIdentifier, the unique matching Cloud account/device path, Local Hourly device/user metadata, and securely decoded CloudKit record identities must agree. Daily and Weekly metadata must have the same nonfuture refresh timestamp from today. Every elapsed day in the native week must have a native Daily record, and their per-app sum must reconcile exactly with Weekly. Missing earlier days and unexplained future contributions fail closed; an uncovered historical day does not block a covered today.

Promotion strips CloudKit record identities and uses the Local envelope without modifying Cloud. Category aggregates follow the same app-sum policy; outside-selected-day weekly app contributions remain unchanged. Cloud input hashes, local device identity and absent destination paths are included in the verified backup/revision inventory. Disposable production-path tests verify creation absence, subsequent writes and exact restoration; release checks never Apply on a device.

Trusted native per-app/category templates remain required. A valid Cloud baseline does not authorize inventing an absent app's category. Read-only XS Max verification accepted Oct19's Cloud day/week while rejecting Oct17 independently; the requested App Store plus Calculator plan still fails closed because their native templates are absent from current caches. Two verified backup archives contain an App Store template but no Calculator template. No device Apply was performed.

The blanket iOS 18.0–18.5 Apply denial was removed at Lucas's request. He reports that Apply and Settings worked on this XS Max 18.3, and that a later immediate Settings crash clears after lock/unlock. That recovery does not establish the crash cause.

Post-write refresh already signals Preferences, ScreenTimeSettingsAgent, ScreenTimeAgent, UsageTrackingAgent and biomed. It now waits a bounded number of probes (101, spaced 20ms apart) for the signalled PIDs to disappear or change names, rather than acknowledging the signal itself as completion. Probe errors and exit timeouts return refresh failure, which Apply reports with the verified backup ID as a partial Apply failure. No replacement process is signalled during this wait. The same-name PID-reuse case conservatively times out.

Exit acknowledgement is not a cache-ready handshake, does not reproduce lock/unlock, and is not proof that the transient Settings crash is fixed. Synthetic barrier tests cover immediate exit, delayed exit, timeout, probe failure, multiple PIDs and invalid bounds. Live crash diagnosis still requires saved cache comparison and native Settings verification. No live Apply was performed for this revision.

The earlier read-only crash investigation matched XS Max DeviceActivity UUID 7D88FD34-405A-31D5-A10C-1FC33F39ABF6 and a Preferences Foundation DateInterval.init(start:end:) stack at DeviceActivity offset 342284. That is evidence of an invalid refresh interval on that path, not proof that every Apply fails on iOS 18.3. The captured crashes predate Lucas's reported working test. The exact difference between working and crashing data remains unresolved.

Cloud-only Local initialization is now supported narrowly when all three existing Local segment directories are completely empty and all three metadata files are absent. A partial Local layout remains authoritative and cannot bootstrap. No directory is created during planning.

Bootstrap anchors provenance in the actual same-device Cloud Hourly metadata instead of requiring a nonexistent Local Hourly record. Its known device/user schema, secure CKRecord type/name/zone, and device identifier must validate. Hourly, Daily and Weekly refresh times must agree, be nonfuture, belong to today, and be no more than one hour old. Native Hourly records provide templates, never invented historical usage. Every closed day of the week still requires its own validated Daily record and exact per-app reconciliation with Weekly.

Identity-stripped Local envelopes retain the verified native device/granularity zone convention. Plans target Local exclusively, including missing Hourly metadata; Cloud is never a write destination. The existing transaction inventory archives Cloud source proofs, calendar/device identity, and every absent destination before any future user Apply. Exclusive creation and revision checks reject daemon races. The normal Gemini refresh hold remains unchanged.

Release verification used the actual XS Max snapshot on the Mac only. The production read-only planner accepted Settings 00:00–12:04 as 43,440 seconds, produced 29 absent Local plans, preserved each app's outside-day Weekly contribution, and left every captured plist hash unchanged. No live Apply, backup, restore, usage write or cache write was performed. This proves planning against that captured snapshot, not live post-Apply Settings behavior or a general crash fix.
